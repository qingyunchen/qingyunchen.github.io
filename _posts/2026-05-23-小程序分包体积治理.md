# 小程序分包体积治理：被忽视的"跨包引用"陷阱

本文不讨论业务架构，只聚焦于小程序分包机制下一个极易被忽略、却足以导致体积失控的技术细节。

## 一、背景：分包不是万能药

随着业务增长，主包体积触及 2MB 上限，拆分包成为标准操作。

但在实际工程中，很多项目在拆分后依然遇到 "拆完更胖" 或 "莫名其妙超过 2MB" 的问题。  
其根源往往不在于页面多少，而在于 JS 的引用方式。

## 二、核心机制：小程序是如何打包 JS 的？

### 1. 打包粒度：文件级（Module Level）

与 Webpack / Vite 不同，小程序平台的打包逻辑非常"原始"：

- ✅ 以 **文件** 为单位进行打包
- ❌ 不支持 Tree Shaking（函数级剔除）
- ❌ 不支持跨分包 JS 共享

这意味着：
```javascript
import { formatDate } from '../../common/utils/date'
```

即便你只使用了 `formatDate` 这一个函数：

**整个 date.js 文件会被完整打入当前分包**

### 2. 跨分包引用的后果

当一个分包引用了另一个分包的 JS：

| 行为 | 结果 |
|------|------|
| 引用其他分包的 JS | 复制一份到当前分包 |
| 多个分包引用同一份 JS | 每个分包各复制一份 |
| 公共库体积较大 | 分包体积呈倍数增长 |

**结论非常明确：**

❗ 小程序中没有"公共 JS 自动提升"机制  
❗ 跨分包引用 = 强制复制

## 三、典型反模式（高风险）

### ❌ 反模式 1：业务分包共用 utils / request

```
subPackageA/
subPackageB/
subPackageC/
└── common/
    ├── utils.js
    └── request.js
```

三个分包同时引用：
```javascript
import request from '../common/request'
```

📌 **结果：**
- request.js 被复制 3 次
- 分包体积不可控

### ❌ 反模式 2：组件内部引用非主包 JS

```javascript
// components/xxx/index.js
import helper from '../../utils/helper'
```

📌 **结果：**
- 组件无法被多个分包安全复用
- 每个使用该组件的分包都会携带一份 helper

## 四、推荐实践：分包 JS 边界划分

### ✅ 原则 1：公共 JS 必须收敛于主包

所有被 ≥2 个分包引用的 JS，必须放入主包。

**推荐目录结构：**
```
main/
├── request/
├── utils/
├── constants/
├── hooks/
└── components/
```

**分包引用方式：**
```javascript
import request from '@/main/request'
```

### ✅ 原则 2：分包之间禁止 JS 引用

| 引用方向 | 是否允许 |
|----------|----------|
| 主包 → 分包 | ✅ |
| 分包 → 主包 | ✅ |
| 分包 → 分包 | ❌ |

任何跨业务分包的 JS 引用，都应视为红线。

### ✅ 原则 3：组件必须具备"主包可用性"

如果一个组件：
- 被多个分包使用
- 内部引用了 utils / request / helpers

那么它：

**必须放在主包 components 中**

否则必然导致重复打包。

## 五、体积安全线建议

| 指标 | 建议值 |
|------|--------|
| 单个分包体积 | < 1.5MB |
| 公共 JS 总体积 | < 500KB |
| 主包剩余容量 | > 300KB |

超过上述阈值，后续迭代极易触发 2MB 限制。

## 六、跨包跳转性能真相

很多人在拆分包后会有一个疑虑：**跨分包跳转会不会很慢？**

### 结论先行

✅ 跨分包跳转，唯一的性能代价是：**首次进入时下载分包慢一点**

❌ 不会造成运行时性能问题（不会卡、不会内存泄漏、不会影响渲染）

### 官方机制：懒加载 + 缓存

```
分包 A → 分包 B
  ↓
判断是否已下载分包 B
  ↓
没下载 → 下载分包
下载完成 → 跳转页面
  ↓
以后再进 → 直接用缓存
```

👉 **只慢第一次**

### 性能影响拆解

| 指标 | 是否受影响 |
|------|------------|
| 页面渲染速度 | ❌ 无影响 |
| setData 性能 | ❌ 无影响 |
| 组件生命周期 | ❌ 无影响 |
| JS 执行速度 | ❌ 无影响 |
| 内存占用 | ❌ 无影响 |

**跨包页面和普通页面，在运行时没有任何区别。**

### 首次跳转延迟参考

| 分包大小 | 首次进入延迟 |
|----------|--------------|
| < 500KB | 几乎无感 |
| 500KB–1MB | 0.3–0.8 秒 |
| 1MB–2MB | 0.8–2 秒 |
| > 2MB | 不建议存在 |

### 三个"非性能但很坑"的点 ⚠️

**⚠️ 1. 跳转前没有预加载**

很多人直接 `wx.navigateTo()`，用户会感觉到"卡一下"。

✅ **正确做法：**
```javascript
wx.preloadSubpackage({
  name: 'purchaseB'
})
```

**⚠️ 2. 连续跨包跳转叠加延迟**

```
首页 → 分包A → 分包B → 分包C
```

每个分包都没预加载时，延迟会累积。

**⚠️ 3. 分包里"初始化逻辑太重"**

```javascript
onLoad() {
  initSDK()
  loadBigConfig()
  requestAllData()
}
```

这不是分包问题，是页面逻辑问题。

### 安全场景判断

结合前文原则：
- 分包 < 2MB ✅
- 不跨包引用 JS ✅
- 只做页面跳转 ✅

👉 **非常安全，性能影响可以忽略不计。**

## 七、总结

- 小程序 **不具备 JS 共享能力**
- 跨分包引用 JS **一定会复制**
- 公共逻辑 **必须收敛于主包**
- 分包设计的核心是 **边界**，而非拆分数量
- 跨包跳转唯一代价是 **首次下载慢**，不影响运行时性能

真正导致分包爆炸的，往往不是页面，而是"看起来无害的公共 JS"。

如果你正在维护一个长期迭代的小程序项目，建议现在就打开 **代码依赖分析**，检查一下：

有多少 JS 正被悄悄复制进每一个分包？
