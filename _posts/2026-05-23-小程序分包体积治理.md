# 小程序分包体积治理：被忽视的"跨包引用"陷阱

在小程序开发中，**"主包超过 2MB"** 几乎是每个中大型项目的必经之劫。很多开发者在面对这个问题时，第一反应就是“拆分包”。

但你是否遇到过这样的怪事：**页面明明拆出去了，主包体积却没降多少，甚至分包体积还莫名其妙地爆炸了？**

本文不谈玄学架构，只聚焦于小程序打包机制中一个极易被忽略、却足以让体积治理功亏一篑的核心细节：**跨包引用**。

---

## 一、 现状：为什么分包不是“万能药”？

当业务增长触及 2MB 上限时，拆分包（Subpackaging）是官方推荐的解法。但在实际操作中，很多团队会陷入“拆完更胖”的怪圈。

其根源往往不在于页面组件的多少，而在于 **JS 的引用逻辑** 违背了小程序的底层打包规则。

---

## 二、 核心原理：小程序 JS 打包的“原始性”

要治理体积，首先要理解小程序是怎么打包 JS 的。它与我们习惯的 Webpack/Vite 有着本质区别。

### 1. 打包粒度：文件级（Module Level）
小程序平台的打包逻辑非常“原始”：
- **✅ 以文件为单位：** 只要引了某个文件里的一个函数，整个文件都会被打包进去。
- **❌ 不支持 Tree Shaking：** 无法像 Web 端的现代工具那样，只提取用到的函数。
- **❌ 不支持跨分包共享：** 分包之间无法在运行时共享 JS 实例。

### 2. 跨分包引用的“恐怖”后果
当分包 A 引用了分包 B（或非主包公共路径）的 JS 时，会发生以下行为：

| 场景 | 打包结果 | 体积影响 |
| :--- | :--- | :--- |
| **引用非主包 JS** | 该 JS 文件被 **复制** 到当前分包 | ❌ 增加分包体积 |
| **多个分包引用同一 JS** | 该 JS 文件在每个分包里各 **复制** 一份 | ❌❌ 体积呈倍数增长 |
| **引用了大型第三方库** | 每个分包都背着一个沉重的库副本 | ❌❌❌ 瞬间触发体积上限 |

> **核心结论：**
> 在小程序中，**跨分包引用 = 强制物理复制**。没有所谓的“公共 JS 自动提取”机制。

---

## 三、 典型反模式：看看你中招了吗？

### ❌ 坑 1：业务分包共用“灰色地带”的 utils
如果你的公共代码放在一个既不属于主包、也不属于任何业务分包的“三不管”地带（如根目录下的 `common/`），且没有被主包显式引用。

**后果：** 每个引用的分包都会把 `common/` 下的代码完整 Copy 一份。

### ❌ 坑 2：组件“背刺”
一个放在主包的组件，如果它内部 `import` 了一个只存在于某个分包或 `common` 路径下的工具函数。

**后果：** 只要这个组件被多个分包使用，那个工具函数就会被无限复制。

---

## 四、 治理方案：构建清晰的 JS 边界

为了彻底解决“重复打包”问题，我们需要建立一套严苛的 **JS 引用红线**。

### 1. 引用金律（The Golden Rules）
| 引用方向 | 是否允许 | 治理动作 |
| :--- | :--- | :--- |
| **主包 ➔ 分包** | ✅ | 正常使用 |
| **分包 ➔ 主包** | ✅ | 正常使用 |
| **分包 A ➔ 分包 B** | ❌ **绝对禁止** | 将共有逻辑提取至主包 |
| **分包 ➔ 非主包 Common** | ⚠️ **高危** | 确保该 Common 逻辑被主包引用或移入主包 |

### 2. 目录结构：按业务线拆分（推荐方案）
小程序分包的本质，应该是 **业务拆分** 而非技术拆分。

```text
main/                # 【主包】全局公共逻辑、首页、TabBar 页面
├─ request/          # 网络请求封装
├─ utils/            # 全局工具函数
├─ components/       # 高频全局组件
└─ constants/        # 全局常量

purchase/            # 【分包 A】采购业务线
├─ pages/            # 业务页面
├─ components/       # 仅本业务使用的组件
└─ utils/            # 仅本业务使用的工具函数

order/               # 【分包 B】订单业务线
└─ ...
```

**为什么按业务线分包最稳？**
- **低耦合：** 同业务线内跳转极少跨包，逻辑自闭环。
- **可预测：** 谁开发业务，谁负责该分包体积，责任清晰。
- **易维护：** 新增业务 = 新增分包，不会对老包造成体积挤压。

---

## 五、 性能真相：跨包跳转真的慢吗？

很多开发者不敢大刀阔斧拆分包，是担心跨包跳转的性能。

### 1. 结论：只慢“第一次”
跨分包跳转唯一的代价是：**首次进入时需要下载分包。**
- **❌ 运行时：** 无任何影响（渲染、内存、JS 执行速度均与普通页面一致）。
- **✅ 解决之道：** 使用官方提供的 **分包预下载（Preload）** 机制。

```javascript
// 在 app.json 中配置，当进入首页时，自动后台下载采购分包
"preloadRule": {
  "pages/index/index": {
    "network": "all",
    "packages": ["purchase"]
  }
}
```

### 2. 体积安全线建议
为了留出足够的迭代空间，建议遵循以下指标：
- **单个分包体积：** 控制在 **1.5MB** 以内。
- **公共 JS 总体积：** 严格控制在 **500KB** 以内。
- **主包剩余容量：** 保持 **300KB** 以上的缓冲带。

---

## 六、 总结：体积治理的“心法”

小程序体积治理不是一次性的“大扫除”，而是一项长期的工程规范。

1. **认知升级：** 记住“跨包引用即复制”。
2. **逻辑收敛：** 被 ≥2 个业务分包引用的 JS，必须提升至主包。
3. **组件解耦：** 确保主包组件不依赖分包 JS。
4. **业务边界：** 坚持按业务线划分分包，实现真正的物理隔离。

**最后的一句建议：**
如果你正在被体积问题困扰，请立即打开微信开发者工具的 **“代码依赖分析”**。你会惊讶地发现，有多少代码正在你的分包里偷偷地“影分身”。
